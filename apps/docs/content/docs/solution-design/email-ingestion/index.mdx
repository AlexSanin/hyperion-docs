# Email Ingestion for Research Capture

We aim to build an automated system for capturing research documents from email, parsing attachments, and processing them through our document intelligence pipeline without manual user intervention.

## Scope

### In Scope

- [x] IMAP protocol support for standard email servers
- [x] Microsoft Graph API support for Office 365
- [ ] Google Workspace API support (Phase 2)
- [x] Dedicated mailbox per tenant (`research@tenant.archon.io`)
- [x] Attachment extraction (PDF, DOCX, XLSX, images)
- [x] Email metadata extraction (sender, recipients, subject, date)
- [x] Thread linking for conversation grouping
- [x] Hash-based deduplication across threads
- [x] Processing pipeline integration (OCR, NER, Classification)
- [x] Slack notifications for new research

### Out of Scope

- [ ] Email sending / reply functionality
- [ ] Calendar integration
- [ ] Contact synchronization
- [ ] Real-time push (polling only for MVP)
- [ ] Attachment size > 100MB

## Research

**1. Email Protocol Selection** — We evaluated IMAP vs Microsoft Graph API. IMAP provides universal compatibility but lacks modern features. Graph API offers richer metadata and push notifications for O365 tenants. Decision: Support both, tenant-configurable.

**2. Polling vs Push** — Graph API supports webhooks for real-time notifications, but IMAP requires polling. For MVP, we implement polling with configurable intervals (5min-1hr). Push support planned for Phase 2.

**3. Attachment Handling** — Large attachments (>50MB) can timeout during processing. Solution: Stream directly to S3, process asynchronously. Implement size limits with clear user feedback.

**4. Thread Detection** — Email threads are identified via `In-Reply-To` and `References` headers. We normalize thread IDs and link related documents for context.

**5. Deduplication Strategy** — Same attachment may arrive in multiple threads (forwards, replies). SHA-256 hash on content prevents duplicate processing. SimHash catches near-duplicates (minor formatting changes).

## Risks & Solutions

### Technical Risks

| Risk                       | Impact                     | Mitigation                                                          |
| -------------------------- | -------------------------- | ------------------------------------------------------------------- |
| OAuth token expiry         | High — ingestion stops     | Implement auto-refresh, monitor token TTL, alert 24hr before expiry |
| Email provider rate limits | Medium — delayed ingestion | Implement exponential backoff, respect `Retry-After` headers        |
| Large attachments timeout  | Medium — documents stuck   | Stream to S3 first, process async, implement timeout limits         |
| Malformed emails           | Low — parsing errors       | Graceful degradation, log errors, skip unparseable with alert       |

### Stability Concerns

- [ ] If email provider is down, ingestion pauses (no data loss, resumes on recovery)
- [ ] OAuth credential rotation requires tenant admin action
- [ ] Polling intervals affect freshness vs API quota trade-off

### User Communication

- [ ] Tenant onboarding guide for mailbox setup
- [ ] Email forwarding instructions for users
- [ ] Processing status visibility in UI
